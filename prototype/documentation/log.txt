[2026-06-17]  Directionality Mapping — using an LLM on the screens Phase 1 could not orient
================================================================================

BACKGROUND
----------
- The original design documents (proposal / architecture diagram / slides, under context/) name
  "directionality" as RETICLE's number-one problem: BioGRID gives rank order, not direction. The
  architecture diagram has two dedicated agents for it, "Directionality Mapping" and "Biological
  Sanity Checks".
- Phase 1 (harmonize_scores.py) settled 86% of screens with deterministic rules, because the
  score carries its own direction (log2FC, CERES, and so on). 111 screens it could not settle:
    * 100 AMBIGUOUS_SELECTION: only an undirected significance column (p-value / STARS / MaGeCK
      p / ...), and an unclear SCREEN_TYPE (Phenotype Screen, Positive and Negative Selection)
      -> the old code simply guessed sel=+1.
    *  11 UNRESOLVED: no usable effect column at all (only read counts / sgRNA number / rank).
- BioGRID's NOTES field, present on 96.3% of screens, was found to state the polarity outright
  surprisingly often. Screen 89, for example: "negative MaGeCK score = cell-essential genes,
  KO -> decreased proliferation". That is exactly the information orientation needs.

DECISIONS
---------
1. The LLM's job in this project moved from "control_comparison" (which had no downstream use)
   to "directionality".
   - Dropped control_comparison / confidence_control from screen_metadata_curated.
   - llm_metadata_extractor.py became purely rule-based (screen_type / selection / coverage) and
     no longer calls an LLM.
2. Architecture: the LLM runs ONCE and emits a frozen JSON artifact,
   processed_data/directionality_overrides.json, which harmonize / apply_directionality read as a
   deterministic input. Phase 1 therefore stays a pure function and the model's
   non-determinism is quarantined in the artifact-generation step.
3. Low confidence (<0.7) or UNDEFINED -> needs_review, not applied automatically; a human rules.
4. Anchor conflicts: first try a stronger model (below); anything still conflicting is corrected
   against essential-gene ground truth.

FILES ADDED / CHANGED
---------------------
- script/directionality_mapper.py   (new) LLM direction ruling -> overrides.json
- script/apply_directionality.py    (new) non-destructive in-place apply + essential-gene veto
- script/harmonize_scores.py        extracted reusable functions (load_screen_df /
                                    add_rank_columns / apply_override / load_overrides) and an
                                    override hook (active only when overrides.json exists; the
                                    refactor was verified gene-by-gene on screen 381 to be
                                    behaviour-preserving)
- script/llm_metadata_extractor.py  now rule-only (v4.0-rules-only)
- processed_data/directionality_overrides.json  (new) the frozen artifact

THE SHARED AXIS (what the LLM aligns to)
----------------------------------------
  +1 = loss of function is advantageous / enriched in the selected population (the gene normally
       promotes the bad outcome)
  -1 = the gene is essential / required for the phenotype (knockout depletes, as core essentials do)
  Note: perturbation direction (CRISPRa and friends) is folded in by the LLM as it reasons over
  NOTES, so the emitted value is already the final sign.

RUN RESULT (gpt-4o, temperature=0)
----------------------------------
  target: 111 (AMBIGUOUS=100, UNRESOLVED=11)
  tokens: prompt ~87,545 + completion ~8,880  (~96K, a few cents)
  mapper output: auto=71  needs_review=29  binary_only=11
  applied: 71 (LLM_SINGLE=64 + LLM_PAIR=4 + ANCHOR=3)
  whole-database sanity check (validate_harmonization.py): PASS
     — core essential genes stay on the negative end across all 11 analysis methods; the
       direction corrections did not damage existing data.

INCIDENTS AND HOW THEY WERE HANDLED
-----------------------------------
1. gpt-4o-mini ruled screen 89 (a PAIR) backwards, and reported confidence=1.0.
   - Symptom: positive_column / negative_column swapped; essential-gene mean_pct = +0.274, which
     should have been negative.
   - Caught by apply_directionality's essential-gene veto gate (essential genes on the positive
     end of a KO proliferation screen means the direction is backwards).
   - Conclusion: a confidence threshold is NOT sufficient to catch an error. The biological
     sanity check is required.
   - Action: upgraded to gpt-4o, per the user's decision. gpt-4o ruled 89 correctly
     (+SCORE.3 / -SCORE.1), and gave 172 (a BMP activator) = -1 against 173 (a BMP inhibitor)
     = +1 — opposite signs, which is the internally consistent answer.

2. gpt-4o still misread three: screens 1050 / 1052 / 1053.
   - Layout {SCORE.1=MaGeCK Score, SCORE.2=p-Value, SCORE.3=FDR}. These are SINGLE, but the model
     called them PAIR (+SCORE.1 / -SCORE.2), treating the p-value as an independent enrichment
     column.
   - Caught by the veto gate (essential-gene mean_pct = +0.262 / +0.312 / +0.227).
   - Action (user-approved): orient them deterministically from core essential genes. All three
     are KO proliferation screens containing 10 core essential genes each, where the rule is
     absolute — essential genes must be negative.
     apply_directionality.py --anchor-resolve-conflicts:
       re-ruled as SINGLE, taking whichever sign puts the essential genes on the negative end,
       i.e. sign -1.
       Resulting ess_mean_pct: 1050 -0.443 / 1052 -0.456 / 1053 -0.367  (correct)
     The decision is written back into overrides.json (resolution="essential-gene-anchor") so the
     result stays reproducible.

FINAL DIRECTION STATE (screen_metadata.SCORE_BASIS)
---------------------------------------------------
   64  LLM_SINGLE          (gpt-4o, high-confidence single-column orientation)
    4  LLM_PAIR            (pos/neg pair identified by gpt-4o)
    3  ANCHOR_SINGLE       (corrected from essential-gene ground truth: 1050, 1052, 1053)
   29  still AMBIGUOUS     (needs_review, see below)
   11  UNRESOLVED          (binary_only, see below)
  The other ~2,046 remain Phase 1's deterministic result, untouched.

OUTSTANDING
-----------
- needs_review (29): gpt-4o returned UNDEFINED — the BioGRID text for these screens genuinely
  does not state a polarity.
  screen ids: 1081,1082,1083,1441,1442,1443,1444,1445,1446,1447,1448,1697,1698,
              1699,1700,1701,1712,1718,2326,2328,2329,2330,2331,2336,2337,2338,
              2340,2341,2342
  They still sit at the old hard-guessed sel=+1. Options on the table: (a) route them to the
  binary path and keep them out of continuous correlation, (b) leave as is, (c) fetch the paper's
  Methods section and rule from that. Not yet decided by the user.
- binary_only (11): UNRESOLVED, no continuous effect column. These belong on the IS_HIT set path
  in Phase 3 (Jaccard / Fisher).
  screen ids: 145,630,690,1043,1044,1173,1174,1198,1211,1232,1742

HOW TO REPRODUCE
----------------

  python3 script/validate_harmonization.py

[2026-06-21]  assay_domain stratification — fitness / stress / reporter
================================================================================

BACKGROUND
----------
- Pooled statistics were mixing screens of different phenotype and diluting the signal. The
  clearest case: POLA1 is pan-essential, yet its median across ALL screens is only -0.75, because
  drug / virus / reporter screens are folded in, and POLA1 does not necessarily deplete there.
- The root cause is NOT harmonization. Percentile is a within-screen rank and is correct for
  every screen individually. The problem is aggregating or correlating ACROSS screens whose axes
  mean different things. Harmonization's sign maths is one shared survival axis and should stay
  that way; the right fix is a stratification label that downstream code groups by.

DECISION
--------
  Tag every screen with an assay_domain (deterministic rule, derived from PHENOTYPE — free, no
  LLM):
    fitness  — baseline growth / viability. The only place essentiality is read, and the clean
               pool for continuous correlation.
    stress   — survival under an applied pressure (drug / virus / toxin ...). Conditional
               fitness; mainly comparable within the same pressure.
    reporter — sorted on a marker (FACS); does not measure survival. Each marker is its own axis,
               so these are excluded from the quantitative axis and the correlation network, and
               used only for per-gene functional annotation.
    other    — fallback (handled like reporter).
  The key point: harmonization does not change. The label only governs how downstream code
  aggregates, correlates and displays.

FILES CHANGED
-------------
- script/llm_metadata_extractor.py  added rule_assay_domain() and two columns (assay_domain,
                                    confidence_domain), prompt_version=v4.1-assay-domain
- screen_metadata_curated table     dropped and rebuilt; all 2,157 rows backfilled
- web/app.py                        /api/gene became domain-aware: statistics split by domain,
                                    fitness primary, stress secondary, reporter counted plus used
                                    as a functional probe. The interpret prompt is domain-aware too.
- web/index.html                    fitness as the main view (axis + histogram + context), stress
                                    as a compact secondary view, reporter as one line; shows a
                                    "flipped" notice when fitness and stress disagree in sign.

DISTRIBUTION (2,157 screens)
----------------------------
  fitness=1227   stress=700   reporter=230

VALIDATION — splitting by domain reveals the real biology
---------------------------------------------------------
  POLA1: pooled -0.75 -> fitness -0.872 (cleanly essential) / stress -0.258 /
         reporter +0.417 (the source of the dilution)
  KRAS : fitness -0.666 (oncogene dependency) / stress +0.064 (losing it confers resistance to
         some drugs — pooling smears this away)
  TP53 : fitness +0.491 (tumour suppressor; loss is advantageous) / stress +0.186 / reporter ~0

DOWNSTREAM RULES (recommended)
------------------------------
- Read essentiality from fitness only.
- Correlation: fitness is one clean pool; stress within the same pressure; reporter excluded
  entirely (too fragmented — 203 screens spanning 114 markers).
- Keep reporter for precise functional annotation ("Senescence genes", "Regulators of mitophagy").

GOAL
----
  Grow the gene explorer from "BioGRID only" into a multi-source RAG — NCBI/PubMed + GO + STRING
  — and give every gene the proposal's "darkness rating".

DATA SOURCES (the ones that had to be obtained by hand)
-------------------------------------------------------
  - NCBI E-utilities (PubMed counts + abstracts): optional NCBI_API_KEY in .env -> 10/s instead
    of 3/s. Configured.
  - MyGene.info (gene name / summary + GO terms): no key needed.

  - WashU gateway (RAG generation, gpt-4o): already available.

ADDED / CHANGED
---------------
- script/external_sources.py (new) one client for all of them: on-disk cache
  (processed_data/external_cache.db, 30-day TTL) + rate limiting + optional key. Functions:
  gene_annotation (MyGene), pubmed_count, pubmed_pmids, pubmed_abstracts (efetch XML),
  string_partners, darkness, enrich. Every one of them fails soft.
- darkness formula: dark_pub = clamp(1 - log10(P+1)/log10(1000));
                    dark_go  = clamp(1 - log10(G+1)/log10(50));
                    darkness = 10 * (0.6*dark_pub + 0.4*dark_go).
                    0 = well studied, 10 = dark matter.
- web/app.py   added GET /api/context (enrich: darkness + summary + STRING, lazy and cached);
  /api/interpret became RAG: pulls PubMed abstracts (esearch by relevance -> efetch) + STRING +
  darkness, feeds gpt-4o, requires it to cite PMIDs, and asks it to flag de-orphaning candidates
  explicitly when a dark gene behaves like a known pathway. Returns sources (PMIDs).
- web/index.html  added a "Known to science + darkness" band under the gene head (darkness score
  and bar + NCBI summary + STRING partner chips, each clickable through to that gene); the AI
  reading shows PMID citation links.

GOTCHA
------

  human[orgn] / mouse[orgn]. Fixed.

VALIDATION (darkness contrast)
------------------------------

END-TO-END DE-ORPHANING DEMO: C1orf109

[2026-06-22]  Whole-database fix for a sign-inversion bug
================================================================================

HOW IT WAS FOUND
----------------
  On the site, POLR2A (RNA Pol II, pan-essential) showed +1.00 in HL-60 / K-562 and other fitness
  screens — "knockout favored" — when an essential gene in a viability screen must be negative.
  Auditing the whole database using a panel of core essential genes as a probe found 39-42 of the
  971 fitness-KO screens inverted in their entirety.

ROOT CAUSE (not a single bug)
-----------------------------
  Directionality / signedness cannot be inferred reliably from the SCORE.k_TYPE name. Different
  authors use opposite conventions for the same metric name, and even differ on whether it is
  signed at all:
   - same name, opposite convention: Dependency score ([0,1] probability, high = essential) vs
     CERES (negative = essential); Essentiality Score (negative = essential in this batch);
     Mean Depletion; Z-score (62% of screens inverted)
   - signed values treated as magnitude and then clipped at 0: RSA (all negative) / CGI (51%
     negative) / CasTLE Score (signed in screen 18, unsigned in screen 157) — clipping erases the
     essential signal entirely
   - ambiguous or mislabelled selection: pure-significance screens with a wrongly guessed sel
  validate had not caught it because it averages across screens per ANALYSIS, and a minority of
  inverted screens gets diluted away.

FIX (two layers, deterministic, non-destructive)
------------------------------------------------
  harmonize_scores.py registry corrections:
    - DIR_POS gains "mean depletion" and "essentiality score"; loses "dependency score"
    - DIR_NEG becomes {"bayes factor", "dependency score"}
    - the SIG_MAG path gains DATA-DRIVEN SIGNEDNESS: if a column carries substantive negative
      values (>5% of rows and min < -0.5) it is treated as SIGNED_MAG, used as signed, and not
      clipped. This handles RSA / CGI / CasTLE automatically, screen by screen.
  script/fix_directionality.py (new):
    Phase 1 — recompute the 30 screens whose type the registry changed (from the raw files,
              replaced in place)
    Phase 2 — essential-gene anchoring, applied ONLY to FITNESS-KO screens (stress excluded, see
              below): >= 3 core essential genes and a panel mean > 0 -> negate the whole screen
              (exact negation) and mark SCORE_BASIS with [ANCHOR_FLIP]. 32 screens flipped.

WHY STRESS IS NOT ANCHORED
--------------------------
  In a stress screen — particularly a positive-selection resistance screen — essential genes
  deplete in both the treated and the control arm and cancel out, so they legitimately sit near
  zero (the distribution is centred on 0, not on -1). Applying "essential genes must be negative"
  to stress would manufacture new errors. Only fitness is anchored.
  Fitness distribution: 885 of 971 at <= -0.5 (correct); the 42 on the positive end are the real
  inversions.

RESULT
------
  validate_harmonization: PASS; fitness-KO panel still positive: 42 -> 0 of 971
  POLR2A fitness median -0.985; POLR2A fitness > 0.9: 12 -> 3 (the remainder are genuine
  outliers; the panel is still negative)
  No over-correction: stress untouched, near-zero borderline cases untouched.
  WARNING: the essential-gene panel initially held only human uppercase symbols, so it missed
  mouse (Polr2a). After adding the mouse orthologs and re-running, mouse fitness-KO inversions
  went 16 -> 0. Final state: human 0/971 and mouse 0/70, both clean.
  Boundaries: KO fitness is anchor-verified in both species; stress cannot be anchored (essential
  genes sit near zero there) and CRISPRa/i rely on the registry.

LEFT OVER / TODO
----------------
  - correlation_analysis was built on the old (partly inverted) scores. The correlations for the
    62 affected screens need recomputing -> re-run compute_correlations.py next time, ideally
    after making it domain-aware.
  - Reproduce: python3 script/fix_directionality.py  (the registry changes already live in
    harmonize_scores.py, so a future full harmonize rebuild picks them up automatically;
    fix_directionality handles the in-place correction.)
